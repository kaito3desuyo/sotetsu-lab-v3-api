# ロードマップ（api）

2026-10-23 に棚卸しした、次のマイルストーンのうち api が関わる分。各マイルストーンの spec・計画・ADR は着手時に `docs/superpowers/` と `docs/adr/` に書く。

## 全体の順番

M0 後始末 → M1 登録制 ② → M2 SSR → M3 臨時列車 → M4 API の外部公開。M5 過去の目撃データの補完（段1：解析）は M1 と並行。M6 平日・土休日の取り違えの修正は、いつでも差し込める。M7 祝日データの延長は 2027 年のうちに、client の M8 index.html のキャッシュは M1 の告知日より前に。M9〜M11 はいつでも差し込める。性能と費用削減も並行で進めるが、手をつける前に計測する。他のリポジトリの分は、それぞれの `docs/roadmap.md` にある。

## api の分

| M1 | 登録制 ② | 目撃投稿を登録者だけにする（DB のフィーチャーフラグ `registered_only_posting` で公開日を選ぶ）、投稿者の記録（`operation_sighting_authors`）、trip-blocks の書き込みを EDITOR・MANAGER に、書き込み成功時に socket の broadcast 関数を Invoke（d′） | 決定・実装済み（2026-10-23・`docs/superpowers/specs/2026-10-23-registered-only-posting-design.md`・ADR-0009・PR #186）。`next-operation-candidates` の絞り込みは範囲外 |
| M3 | 臨時列車 | 派生カレンダー＋`calendar_dates`、運用の割り当て変更 | `calendars.parent_calendar_id` が「GTFS のメインテーブルに列を足さない」原則とぶつかる件を M2 の最中に決める。spec は `feature/special-trips` |
| M4 | API の外部公開 | Supabase OAuth 2.1 Server のトークンを今の JWKS 検証と RBAC で受ける、外部向けの手引き | M1 の後。着手時に beta が外れたか、refresh token の寿命を確かめ直す |
| M5 | 過去の目撃データの補完 | 段1：相鉄館の 2004-09〜2014 の日次ログを正規化・重複除去し、中間 CSV と件数レポートを作る（DB には触らない）。段2 以降の器づくり（退役編成、2009-11 より前のダイヤ・運番）と取り込みも、ここになる見込み | 段1 のスクリプトを置く場所は着手時に決める。段2 以降の範囲は段1 の結果を見て決める |
| M6 | 平日・土休日の取り違えの修正 | 目撃の運用のダイヤが、その日（4 時より前は前日）に効くダイヤと違うもの約 480 件（2019〜2026・2018 年以前は 0 件）を、正しいダイヤの運用に付け替える。内訳は 3 種類。①古い client が開いた時の「今日のダイヤ」を持ち越した個人の連続（2025-10〜2026-04 の約 150 件、2026/3/14 改正後は 48 件で 43G・26K、2022-05-09 など）、②別の改正のダイヤ（`平日ダイヤ(2009-11-01)` など）に入ったもの 214 件（2019-11〜2022-03。2020-10〜11 に集中し、同じ時期に平日・土休日が逆のもの約 30 件も混ざる。client v1.2.0（2020-10-04）で、起動時の `ParamsService.fetch()` が `TokenResolver` より先に走ると、同じ日の api v1.1.0 の AuthGuard に 401 で落とされ `calendarId` が `''` のまま残る。v1 の `/operations/search` は空の `calendar_id` を条件から外し ORDER BY も無いので、投稿は全ダイヤの同じ運番の `[0]` に付いた。11/19 を最後に止まった理由は未確認）、③その日の目撃の大半がそろって違うダイヤに入った日（2020-08-17（月）の 19 件は、1 人が 06:55〜07:00 に約 10 秒おきに続けて入れたもので①と同じ持ち越し。同じ人が 07:35 からは平日に入れ直しており（63 運用の 9701 は両方にある）、実際は平日ダイヤ。2021-01-11 成人の日の 43 件は、v1 の `calendar.controller.ts` に直書きした祝日が 2020-11-23 までで平日ダイヤを返したもの。当日の 75090d5 で直っており、実際は土休日ダイヤ）。残り約 25 件は 2021〜2024 に散らばる単発。直したら `rebuild-latest-cache` で最新目撃のキャッシュを作り直す。同じ取り違えを見つける SQL を残す | 原因は v3 の投稿（2026-05-30）より前の client。アプリを開いた時の「今日のダイヤ」を持ち続けて運用 id を決め、v2 はそれを確かめずに保存した（同じ人の毎日の投稿が、週末をまたいだ 3/30 から 4/30 まで土休日になり、5/1 から平日に戻っている）。今の API は日付（4 時より前は前日）からダイヤを決めるので、5 月以降は 0 件。運番は投稿者が打った番号なので、付け替え先は同じ運番でよい見込み（①は前後の期間に同じ時刻・同じ運番で正しいダイヤに入っている）。③は 2 日とも走ったダイヤが分かった（2020-08-17 は平日・2021-01-11 は土休日）。付け替えで同じ時間帯に同じ編成・運番が重複する目撃も、消さずに両方残す（2026-10-24 決定） |
| M7 | 祝日データの延長 | 本番の `calendar_dates` は 2027-12-31 で終わっている（2026-10-24 確認）。`db/seeds/`（`seed-calendar-dates-*.ts` と `data/`）の祝日・年末年始・特殊日を延ばして `seed:calendar-dates:*` を流す。データの最終日が近づいたら気づける仕組みを作る | 切れると祝日が平日扱いになり、M6 の 2021-01-11 と同じ取り違えが起きる。気づく仕組みを何にするか（CI の定期実行・起動時のログなど）は着手時に決める |
| M9 | 依存の脆弱性 | Dependabot の警告 4 件（high 1・moderate 2・low 1、2026-10-24 時点）を直す | まず中身を見て、本番に届く経路があるかで直す順を決める |
| M10 | 取り違えの見張り | M6 で残す「目撃の運用のダイヤが、その日に効くダイヤと違う」SQL を定期的に流して 0 件を見張る | M6 と M3 の後。臨時列車の派生ダイヤが入ると「その日に効くダイヤ」の判定が変わるので、SQL もそれに合わせる |
| M11 | 入力ミスの棚卸し | 同名駅の別登録（千川・池袋は路線ごとに別 id）、全線時刻表の並べ替えで見つけた時刻の入力ミス 10 件、v3 で ORDER BY が抜けた残り（agencies の findAll） | M6 と同じく数えてから人が判断する。本番の書き込みはユーザーが流す |
| 並行 | 性能 | 行程（`ItinerarySegmentQuery.findManyByCalendarId`）のプロセス内キャッシュ、全線時刻表の並び順テーブル `trip_block_ranks`、版を持つ `calendar_revisions` | 作る前に CloudWatch で温まったコンテナの残り方を測る。版の引き方・上げ方など未決 4 点 |

## M5 の元データの読み方

- 相鉄館の `past_ope_data/`: Shift_JIS の CSV。1 行が `編成番号,運番,区分,月/日,時分[,投稿者]`。年はフォルダ名から決める
- 1 ファイルは「その日の編成ごとの最新」を切り取ったもの。日をまたいで同じ行が重なり、途中の目撃は残っていない
- 区分の小文字 `a`/`p` は毎日 2 時の自動順送りで出た運番であり、目撃ではない
- 運番 `100` は「休」（どの運用にも入っていない）
- `770607004` は当時の表記で 7706(7004)、`97007` は旧7007。呼び方の規則（横浜側先頭車＋F）では 7004F
- 当時の運用図表（`un-yo-zuhyo*.txt`）が 2000/04〜2012/04 の改正ごとに残っている
