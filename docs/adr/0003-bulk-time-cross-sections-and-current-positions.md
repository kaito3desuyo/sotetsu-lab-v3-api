# ADR-0003: リアルタイム運用情報の時刻断面・現在位置をまとめて返す口を足す

- **日時**: 2026-10-01
- **Agent**: claude-opus-5-5
- **ステータス**: 採用済み
- **ブランチ**: feature/redesign-2026-07

---

## 背景

- リアルタイム運用情報（client）は、運用番号の時刻断面・編成番号の時刻断面・運用の現在位置を 1 件ずつ取っていた。
- 手元の実測（2026.3改正 平日ダイヤ）では、この 3 種類だけで運用 104 本・編成 126 本・現在位置 105 本、合わせて 335 本のリクエストになっていた。ページ全体では 374 本で、開き終わるまで 19 秒かかっていた。

## 決定

- まとめて返す口を 3 本足す。1 件ずつの口は残す。
  - `GET /v3/operation-sightings/time-cross-section/operation-numbers?operationNumbers=11,12,…`
    - 返すのは `{ [運用番号]: 時刻断面 }`。休車の 100 は省く。
  - `GET /v3/operation-sightings/time-cross-section/formation-numbers?formationNumbers=10701,…`
    - 返すのは `{ [編成番号]: 時刻断面 }`。
  - `GET /v3/operations/current-positions?operationIds=…`
    - 返すのは現在位置の配列で、入力と同じ順。見つからない運用は省く。
- 3 本とも `searchTime` を受ける。指定がなければ、その瞬間の時刻を 1 つ決めて全件に使う。
- 時刻断面の判定（ADR-0001）は書き換えない。判定が読む DB の口を `TimeCrossSectionSource` にまとめ、読み方だけを差し替える。
  - 1 件ずつの口は、これまでどおりその都度問い合わせる。
  - まとめて返す口は、次のように読む。
    - 対象の番号の最新目撃は、`unnest` と `LATERAL` を使って 1 回の問い合わせで引く。判定で次に要るもの（運用番号側なら編成の最新目撃キャッシュ、編成番号側なら運用番号の最新目撃）も、同じように 1 回で引く。
    - ダイヤ・群のキャッシュ・編成一覧・運用一覧は、引数が同じなら 1 回だけ引く。群のキャッシュは、番号を並べ替えた集合をキーにする。
- 現在位置は、運用と列車を `IN` の 1 回の問い合わせで引く。位置の計算は、1 件ずつの口と同じ関数を使う。

## 却下した案

- **1 件ずつの処理を API の中で並べて回すだけ**
  - DB の接続は 1 本（`database.config` の `max: 1`）なので、問い合わせは順に流れる。
  - 実測では運用番号 10.4 秒・編成番号 10.7 秒・現在位置 4.9 秒で、かえって遅くなった。
  - 本番では、今の 1 件ずつの取り方なら Lambda が並んで動くのに、この案では 1 台に詰め込むことになる。API Gateway の 29 秒の上限にも近づく。
- **最新目撃を `DISTINCT ON` で引く**
  - 全履歴を読むので、運用番号側が 6.6 秒かかった。
  - `LATERAL` にすると、1 件ずつの口と同じく `(operation_id|formation_id, sighting_time)` の索引で最新の 1 件だけを読む。
- **DB の接続を増やす**
  - Lambda の台数と本数を掛けた数だけ Supabase への接続が増える。インフラの判断になるので見送った。

## 結果

- 手元の実測（同じ時刻で、1 件ずつの口と全件を突き合わせた）では、次のとおりだった。
  - 運用番号 104 件は 0.55〜0.70 秒で返り、全件一致した（予想編成あり 77 件）。
  - 編成番号 126 件は 0.23 秒で返り、全件一致した。
  - 現在位置 105 件は 0.34 秒で返り、全件一致した（走行中 75 件）。
- リアルタイム運用情報は、リクエスト 374 本・19 秒から、37 本・4 秒になった。
- 公開は API が先。client は新しい口を呼ぶので、API より先に出すと本番で壊れる。
