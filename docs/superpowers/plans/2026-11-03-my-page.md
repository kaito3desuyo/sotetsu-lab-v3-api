# M13 マイページ（api）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ログインしている本人が、自分の目撃の要約と一覧を「裏付け」の判定つきで読める口を 2 本足す。

**Architecture:** 事実を引く SQL を `OperationSightingAuthorQuery` に 1 本足し、判定の規則は read model `SightingCorroboration` に置く。`OperationSightingV3Service` が一覧と内訳を組み、`UserV3Controller` の `/me` の 2 本が本人の id（`req.auth.userId`）で呼ぶ。書き込み・migration は無い。

**Tech Stack:** NestJS 12・TypeORM 1.x（createQueryBuilder）・Vitest＋SWC

**Spec:** `docs/superpowers/specs/2026-11-03-my-page-design.md`

## Global Constraints

- 口は `GET /v3/users/me` と `GET /v3/users/me/operation-sightings?limit=&before=`。`@RBAC(Role.REPORTER, Role.EDITOR, Role.MANAGER)`・`@CacheControl(CACHE_CONTROL.REALTIME)`。
- 本人の id は `req.auth!.userId!` だけから取る。URL や query に userId を受けない。
- `/me` の 2 本は `UserV3Controller` の `@Get('/:userId')` より**前**に宣言する。
- 判定の値は `'corroborated' | 'conflicting' | 'uncorroborated' | 'invalidated'` の 4 つ。
- 判定の材料: 同じ運行日（`sighting_time` を Asia/Tokyo にして 4 時間引いた日付）・同じ `formation_id`・本人以外（author 行の user_id ≠ 本人、または author 行が無い）・有効（`operation_sighting_invalidations` に行が無い）・自分自身の行を除く、の目撃の運用番号。
- 本人の投稿が無効なら判定せず `invalidated`。
- 規則は SQL に書かない（SQL は運用番号の配列を返すだけ）。
- 管理者向けの `/v3/users/:userId`・`/v3/users/:userId/operation-sightings` の応答の形は変えない。
- query は createQueryBuilder。anti-join は `NOT EXISTS`。lodash は使わない。相対 import に `.js`。
- テストはサンドボックス外で流す（`ERR_SWC_NATIVE_CACHE`）。git は push しない・stash しない・パイプ連結しない。署名コミットはサンドボックス外。
- コミットは Conventional Commits＋絵文字、ドメイン名は日本語（目撃情報・利用者）。

## Review Focus

- 4 時ちょうどの境目: 3:59 の目撃と 4:00 の目撃は別の運行日 → Task 1 の query spec で 3:59/4:00 を並べて確かめる。
- 本人の別の投稿だけが同じ編成を見ている → `uncorroborated`（自分で自分を裏付けない）→ Task 1 の query spec と Task 2 の read model spec。
- ゲスト（author 行なし）の目撃が裏付けになる → Task 1 の query spec。
- 他人の無効な目撃は材料にしない → Task 1 の query spec。
- 投稿 0 件の本人: 要約は 0 と null、一覧は `[]`（404 にしない）→ Task 3 の service spec。

### Task 2: 判定の read model

**Files:**

**Interfaces:**
- Consumes: `OperationSightingCorroborationFactsRow`（Task 1）
- Produces:
  ```ts
  export type SightingCorroborationValue = 'corroborated' | 'conflicting' | 'uncorroborated' | 'invalidated';
  export type SightingCorroborationCounts = Record<SightingCorroborationValue, number>;
  export class SightingCorroboration {
      static of(facts: { operationNumber: string; invalidated: boolean; otherOperationNumbers: string[] }): SightingCorroborationValue;
      static count(values: SightingCorroborationValue[]): SightingCorroborationCounts; // 4 つのキーをいつも持つ（0 を含む）
  }
  ```
  doc コメントに spec の規則（4 通り・前後を問わない・運用の付け替えで正しい投稿も conflicting になりうる）を書く。`SightingAuthorMarks` と同じ形。

  - `of({ ..., otherOperationNumbers: ['58S'] })` → `'conflicting'`
  - `of({ ..., otherOperationNumbers: [] })` → `'uncorroborated'`
  - `of({ ..., invalidated: true, otherOperationNumbers: ['12K'] })` → `'invalidated'`
  - `count(['corroborated', 'corroborated', 'invalidated'])` → `{ corroborated: 2, conflicting: 0, uncorroborated: 0, invalidated: 1 }`
