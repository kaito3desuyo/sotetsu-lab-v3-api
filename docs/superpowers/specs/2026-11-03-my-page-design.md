# M13 マイページ（api の分）

2026-11-03。ロードマップ M13「目撃募集とマイページ」のうち api が受け持つ分。client の分（目撃募集の見せ方・マイページの画面）は client の同名の spec にある。ユーザーは設計を私に任せた（「任せる」）。以下の決定はすべて私の判断で、ユーザーの承認はこの spec のレビューで受ける。

## なぜ

11/6 21:00 に目撃の投稿を登録者だけにする（M1 登録制②）。登録してくれた人に、投稿を続ける理由を返したい。自分が出した目撃が何件あって、他の人の目撃と食い違っていないかが見えれば、続ける張り合いになり、間違いにも自分で気づける。

## 作るもの

ログインしている本人だけが読める口を 2 本、`/v3/users/me` の下に足す。書き込みは無い。

| 口 | 返すもの |
|---|---|
| `GET /v3/users/me` | 本人の要約: 投稿数、無効にされた数、裏付けの内訳（裏付けあり・食い違い・他の目撃なし）、最初と最後の投稿日時 |
| `GET /v3/users/me/operation-sightings?limit=&before=` | 本人の投稿の一覧（新しい順・キーセット）。1 件ごとに裏付けの判定を付ける |

- 役割は REPORTER・EDITOR・MANAGER。viewer（BAN 済み）は今の RBACGuard のとおり 403 のまま。
- Cache-Control は `CACHE_CONTROL.REALTIME`（no-store）。個人のデータなので CDN にもブラウザにも残さない。
- 本人の id は `req.auth.userId` から取る。URL に userId を書かせない（他人の id を入れて読む道を作らない）。
- `/me` は `UserV3Controller` の `/:userId` より前に宣言する。`/:userId` は uuid の検めがあるので `me` は 400 になるが、順番で食い合わせを避ける。

## 「裏付け」の判定

ロードマップでは「当たっていたか」と書いた。正解の表は無く、他の人の目撃と合うかどうかしか分からない。だから画面の言葉は「裏付け」にする。

本人の有効な投稿 1 件（編成 F・運用番号 N・目撃時刻 T）について、**同じ運行日**（4 時の境目。`getBaseDate`）の、**本人以外**の有効な目撃のうち、**同じ編成 F** を見たものを集める。

- そのうち 1 件でも運用番号が N なら **裏付けあり**
- 運用番号 N のものが 1 件も無く、別の運用番号のものがあれば **食い違い**
- 同じ編成の他の目撃が 1 件も無ければ **他の目撃なし**

細かい決め:
- 「本人以外」は、author 行の user_id が本人でないもの、と author 行の無いもの（ゲスト・10/23 より前）。ゲストの目撃も裏付けに数える。
- 本人の投稿が無効にされていれば、判定せず **無効** とする。他の人の無効な目撃は材料に入れない。
- 時刻の前後は問わない（前の目撃も後の目撃も裏付けになる）。運用番号の付け替え（同日引き継ぎ・運用の変更）があると、正しい投稿でも「食い違い」になりうる。それは画面で「食い違い＝間違い」と言い切らない文言で受ける（client の spec）。
- 運用 100（休車）への投稿も同じ規則で判定する。特別扱いしない。
- 運用番号は運用 id でなく番号で比べる（同じ番号でもダイヤごとに id が違う。同じ運行日なら同じダイヤなので、番号で足りる）。

置き場:
- 材料を引く SQL は事実だけを返す（本人の投稿ごとに「同じ日・同じ編成・他人・有効」の目撃の運用番号の集合）。判定の規則は SQL に書かず、`libs/operation-sighting/usecase/read-models/` の read model に置く（規則を SQL に書かない・`SightingAuthorMarks` と同じ流儀）。
- 一覧は本人のページ（最大 200 件）の目撃 id をまとめて 1 本の SQL で引く。N+1 にしない。
- 要約の内訳は全件が要る。今は登録者 5 人・734 件なので、本人の全投稿に同じ SQL を当てて read model で数える。件数が 1 人 1 万件を超えるようになったら考え直す（今は作らない）。

## 流用

- 一覧: `OperationSightingAuthorQuery.findManyByUserId`（M18）。返す形 `OperationSightingSummaryDto` に `corroboration: 'corroborated' | 'conflicting' | 'uncorroborated' | 'invalidated'` を足した DTO を返す。管理者向けの `/v3/users/:userId/operation-sightings` の形は変えない。
- 要約: `UserQuery.findUserSummary`（M18）に内訳を足した DTO。BAN の真偽は本人には返さない（BAN なら 403 で入れない）。

## 作らないもの

- 他の人との比較・順位・正答率の数字。投稿の数を競わせると、雑な投稿が増える。
- 裏付けの通知。
- ゲストの投稿・10/23 より前の投稿をさかのぼって本人に紐づけること（author 行が無い。client で「10 月 23 日より前の投稿は出ない」と書く）。
- 「今日まだ目撃の無い運用」の口。目撃募集は client が今ある取得から導く（client の spec）。

## 確かめ方

- 判定の read model を、4 通り（裏付けあり・食い違い・他の目撃なし・無効）と、本人の別投稿しか無い場合（＝他の目撃なし）、ゲストの目撃で裏付く場合で単体テストする。
- SQL の spec で、日の境目（3:59 と 4:00）、他人の無効な目撃を除くこと、本人の目撃を除くことを確かめる。
- controller の spec で、REPORTER が読め、ゲスト（役割なし）は 403、別人の userId を渡す道が無いことを確かめる。
- 本番 DB で、5 人の内訳を SQL で数えた値と口の値が合うことを確かめる。
